#### Issues Found

**1. [HIGH] INCORRECT_LOGIC**

- **Description**: AbstractBlockCreator computes the new header's excessBlobGas from parentHeader excess plus the blob count of transactions selected for the current block (newBlobsCount -> blobGasCost(newBlobsCount)). The spec defines header excess_blob_gas as the value prior to the block, derived only from the parent header. This also conflicts internally with ExcessBlobGasCalculator.calculateExcessBlobGasForParent, which correctly uses parent blobGasUsed. On the next block, calculateExcessBlobGasForParent would add the same parent blob gas again, double-counting it.
- **Spec Reference**: `def calc_excess_blob_gas(parent: Header) -> int: if parent.excess_blob_gas + parent.blob_gas_used < TARGET_BLOB_GAS_PER_BLOCK: return 0 else: return parent.excess_blob_gas + parent.blob_gas_used - TARGET_BLOB_GAS_PER_BLOCK; excess_blob_gas is a running total of blob gas consumed in excess of the target, prior to the block.`
- **Code Location**: `ethereum/blockcreation/src/main/java/org/hyperledger/besu/ethereum/blockcreation/AbstractBlockCreator.java: computeExcessBlobGas(TransactionSelectionResults, ProtocolSpec), approx. line 350; also evm/src/main/java/org/hyperledger/besu/evm/gascalculator/CancunGasCalculator.java: computeExcessBlobGas(long,int)`
- **Potential Impact**: Locally created blocks can have an excess_blob_gas that other clients and the spec validator reject, causing consensus/proposal failures. If accepted by similarly incorrect nodes, blob gas prices drift upward too quickly because current-block blob use is counted twice.
- **Suggestion**: In AbstractBlockCreator, set header excessBlobGas using calculateExcessBlobGasForParent(newProtocolSpec, parentHeader) / parent excess plus parent blobGasUsed only, while setting blobGasUsed separately from the current block's selected blobs. Remove or rename the ambiguous int-count overload so callers cannot confuse blob count, current-block gas, and parent gas.

**2. [MEDIUM] MISSING_CHECK**

- **Description**: The reviewed files define TARGET_BLOB_GAS_PER_BLOCK and GAS_PER_BLOB but contain no MAX_BLOB_GAS_PER_BLOCK constant or check that the summed blob gas of selected blob transactions is <= 786432 before writing blobGasUsed into the header.
- **Spec Reference**: `| `MAX_BLOB_GAS_PER_BLOCK` | `786432` |; # ensure the total blob gas spent is at most equal to the limit assert blob_gas_used <= MAX_BLOB_GAS_PER_BLOCK; # ensure blob_gas_used matches header assert block.header.blob_gas_used == blob_gas_used`
- **Code Location**: `ethereum/blockcreation/src/main/java/org/hyperledger/besu/ethereum/blockcreation/AbstractBlockCreator.java: computeExcessBlobGas/createBlock header building; evm/src/main/java/org/hyperledger/besu/evm/gascalculator/CancunGasCalculator.java: blobGasCost/computeExcessBlobGas`
- **Potential Impact**: If transaction selection does not enforce the cap elsewhere, the creator can assemble blocks exceeding the blob gas limit that validating clients reject, wasting proposal opportunities and increasing bandwidth/DoS surface.
- **Suggestion**: Add an explicit MAX_BLOB_GAS_PER_BLOCK limit in the gas calculator/selection path and assert in block assembly that blobGasCost(totalBlobs) <= MAX_BLOB_GAS_PER_BLOCK before building the header.

**3. [MEDIUM] MISSING_CHECK**

In the reviewed files it does not reject zero-blob blob transactions, does not check that every versioned hash starts with VERSIONED_HASH_VERSION_KZG (0x01), and does not itself verify max_fee_per_blob_gas >= current blob gas price or the blob-specific balance component; it only forwards blobGasPrice to BlockTransactionSelector, whose implementation is not among the reviewed files.

- **Suggestion**: Add defensive validation during selection/final block assembly, and ensure the execution-layer block validator implements the same checks: at least one blob, 0x01 versioned-hash prefix, blob fee willingness, and balance >= gas*max_fee_per_gas + total_blob_gas*max_fee_per_blob_gas.
